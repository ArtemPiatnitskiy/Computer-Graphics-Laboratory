## Что уже сделано и изучено

- Геометрия тора: `makeTorus(0.8f, 0.35f, 128, 64)`, 8192 вершины, 49152 индекса. Общие vertex/index buffer можно использовать для обоих торов.
- `Vertex` содержит позицию, аналитическую гладкую нормаль и процедурный RGB. Vertex attributes: `location = 0/1/2`, общий vertex binding 0.
- Длинная инициализация разбита на функции; создание graphics pipeline — на helpers для состояний. Пользователь хочет понимать назначение каждой функции и каждого параметра, а не копировать длинные листинги.
- Push constants заменены на uniform buffer. `TransformUniforms` содержит `model`, `view`, `projection`, `color`, поля с `alignas(16)`. Размер при текущих типах — 208 байт. Шейдер объявляет `layout(std140, set = 0, binding = 0) uniform Transform` с теми же полями.
- `makeModelMatrix()` строит `T * R * S` по `object_position`, `rotation_x_degrees`, `object_scale`. Она не вычисляет анимацию. Угол объекта хранится в градусах; в `glm::rotate()` попадает после единственного `glm::radians()`.
- Камера: `glm::lookAtRH`, eye `(0,0,4)`, target `(0,0,0)`, up `(0,1,0)`.
- Проекции: `perspectiveRH_ZO` с вертикальным FOV 50°, near 0.1, far 100; `orthoRH_ZO` с half-height 1.8 и half-width `1.8 * aspect`. В обоих случаях инвертируется `[1][1]`. Интерфейс переключает режимы 1 и 2.
- Ползунки позиции, вращения X, положительного масштаба; `ColorEdit3`. Итоговый цвет вершины — процедурный RGB, умноженный на цвет интерфейса, затем на освещение.
- Нормали преобразуются в vertex shader через `transpose(inverse(mat3(model)))`, нормализуются в fragment shader. Направленное освещение и фоновая составляющая дают объём.
- Анимация: синусоидальные колебания с огибающей `(1 - cos(phase)) / 2`, четыре колебания Y за цикл огибающей, движение по X и небольшое по Z. Флаг `is_animate`, скорость `animation_speed`, параметр `trajectory_size`.
- По просьбе пользователя анимация меняет **те же** `object_position` и `rotation_x_degrees`, которые показывают ползунки. `animateFigure(time)` вызывается перед построением ImGui. На паузе ручное управление остаётся доступным.
- Анимация прибавляет разность смещений новой и предыдущей фазы, а вращение — только за `phase_step = speed * delta_time`. Угол ограничивается эквивалентным значением через `std::remainder(angle, 360.0f)`. `previous_time` обновляется и при паузе, поэтому возобновление не учитывает всё время остановки.
- Пользователь подтвердил, что анимация и связанное с ней ручное управление работают. Два вычисления `makeAnimationOffset()` за кадр оставлены осознанно: оба используют текущий `trajectory_size`, поэтому изменение размера не добавляет скачок от разницы старого и нового размера. Кешировать предыдущее смещение можно, но надо согласовывать кеш с изменением параметров; это не приоритет перед сдачей.

## Текущий перенос ресурсов на два объекта

В `source/application.cpp` уже есть:

```cpp
struct ObjectResources {
    VkBuffer uniform_buffer = VK_NULL_HANDLE;
    VmaAllocation uniform_allocation = nullptr;
    VkDescriptorSet descriptor_set = VK_NULL_HANDLE;
};

constexpr uint32_t OBJECTS_COUNT = 2;
std::array<ObjectResources, OBJECTS_COUNT> objects{};
```

Одиночные глобальные `uniform_buffer`, `uniform_allocation`, `descriptor_set` удалены. Общие layout, pool, pipeline и геометрические буферы сохранены.

Пользователь выбрал такие сигнатуры (они отличаются от примера ассистента; не переделывать их без необходимости):

```cpp
void createUniformBuffer(ObjectResources& object);
void updateUniformBuffer(const TransformUniforms& transform,
                         const uint32_t& object_index);
void writeUniformBufferDescriptor(ObjectResources& object);
```

- Создание пишет buffer и allocation в переданный объект.
- Обновление копирует данные в `objects[object_index].uniform_allocation`; при вызове обязательно передать индекс 0 или 1. Маленький индекс можно позже передавать по значению; это не препятствие для продолжения.
- Запись дескриптора берёт buffer и set из одного объекта; binding 0, offset 0, range `sizeof(TransformUniforms)`.
- Pool: `maxSets = OBJECTS_COUNT`, запас uniform descriptors `descriptorCount = OBJECTS_COUNT`, `poolSizeCount = 1`.
- `allocateDescriptorSet()` по-прежнему выделяет один набор за вызов из общего pool и общего layout.
- `initialize()`: геометрические буферы → descriptor layout → pool → цикл по `objects` (создать UBO, выделить set, записать descriptor) → pipeline layout → graphics pipeline.
- `createPipelineLayout()` сохраняет `setLayoutCount = 1`. В shader остаются `set = 0, binding = 0`; это один слот, в который поочерёдно привязываются два разных набора.

## Что ещё не перенесено

На момент проверки `render()` всё ещё:

- создаёт только один `TransformUniforms transform`;
- вызывает старую форму `updateUniformBuffer(transform)` без индекса;
- привязывает удалённую глобальную `descriptor_set`;
- записывает один `vkCmdDrawIndexed`.

`shutdown()` всё ещё уничтожает удалённые глобальные `uniform_buffer` и `uniform_allocation` вместо цикла по объектам.

Это незавершённый перенос, а не подтверждённая работа двух объектов. Сборка **8 октября после проверки этого снимка не прошла**: ошибки в этих старых обращениях и отсутствие второго аргумента `updateUniformBuffer`. Инициализация по чтению кода соответствует схеме, но её запуск в новом состоянии ещё не проверен. В этот этап сохранения заметок исходники не менялись.

## Ближайшие действия в новом чате

1. В `render()` оставить первый `transform` для текущего управляемого тора; сделать второй блок с теми же view/projection, но собственной model и color. Предлагалось: позиция второго `(1.6,0,0)`, масштаб `0.45`, цвет `(0.5,0.8,1,1)`. Это пример расположения, не требование преподавателя; при необходимости развести фигуры по экрану.
2. Собрать два блока в `std::array<TransformUniforms, OBJECTS_COUNT>` и скопировать каждый в свой UBO через фактическую сигнатуру `updateUniformBuffer(transforms[i], i)`.
3. Общие pipeline, vertex/index buffer, viewport/scissor привязать один раз. В одном render pass для каждого объекта привязать `objects[i].descriptor_set` в `firstSet = 0`, `descriptorSetCount = 1`, затем выполнить `vkCmdDrawIndexed`.
4. После ожидания очереди в `shutdown()` уничтожить UBO каждого объекта. Pool уничтожить один раз; его уничтожение освобождает оба descriptor set.
5. Собрать, запустить, проверить два тора, независимость их данных, управление первым, анимацию/паузу, проекции, resize и validation layers. Не объявлять ЛР законченной только по успешной компиляции.

Объяснить при этом: два draw записывают команды, GPU выполняет их позднее. Простая перезапись одного и того же UBO между записью двух draw не создаёт две копии данных для GPU. Именно отдельные буферы и наборы позволяют обоим объектам читать свои матрицы.

Синхронизация сохраняется: `main.cpp` вызывает `update()` → `prepare()` → `render()` → `submitAndPresent()`. `prepare()` ждёт fence единственного кадра в работе. Копирование данных в UBO остаётся в `render()`, после ожидания; переносить его в `update()` нельзя без изменения схемы синхронизации.
